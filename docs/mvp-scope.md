# Typign MVP仕様案

更新日: 2026-10-20。企画段階の推奨仕様。実装済み機能を示すものではない。

## MVPで答える問い

**学習データを読むAIコーチと、根拠を確認しながら練習を組み立て、別の文章でも打ち直しを減らせるか。**

MVPは、根拠付きのセット提案、会話による時間・重点の変更、実施後の振り返りまでを含む。LLMコーチを後から加える旧案を更新する。学習効果が既に証明されているという意味ではない。

スピード、正確性、苦手、新パターンの4種類を、目的別に選べる構成をMVPに含める。入力エンジンと保存処理は共通にし、教材の選び方、案内、結果の表示を目的に合わせて変える。

提供方式は端末内LLMを第一候補とする。最初は一方式に絞り、日本語の提案・構造化されたセット・変更指示を実機で確認する。未対応環境には標準セットと記録を提供するが、AIコーチを検証したことにはしない。方式の選定は[LLM調査](research/llm-options.md)、Web配信は[技術設計](architecture.md)を参照。

## 対象と入力方式

- 一般公開サイト。登録・ログインは不要。
- デスクトップの日本語ローマ字入力、英単語、基本的な英数記号。
- 最初の保証対象はデスクトップChromeを推奨。macOS/WindowsとJIS/US配列で確認してから対応を明記する。
- 日本語は「日本語の表記＋読み」を示し、IME OFFでローマ字を打つ。英単語・記号は提示された文字をそのまま打つ。
- `し: shi/si`など、サポートした正しい表記を許容する。表記の選択をミスとしない。
- かな直接入力、IME変換・確定、モバイル、音声入力、分割・独自配列は初期の精密診断対象外。

日本語の文章を表示していても、MVPが測る中心はローマ字の打鍵技能。IME変換能力や文章を考える能力のスコアにはしない。

## 画面とユーザーストーリー

| 画面 | ユーザーができること | 完了条件 |
| --- | --- | --- |
| 開始・設定 | 入力方式、配列、目標、時間、コーチの利用可否を確認する | 対象環境と保存場所が分かり、利用できる機能を区別して開始できる |
| 診断 | 短い未見フレーズを入力し、途中で修正する | 正解・誤り・修正をイベントから区別し、結果に反映できる |
| セット | 提案された種類・対象・時間・根拠を確認し、会話で時間や重点を変える | 提案が実行可能なセットへ反映され、本人が選んで開始できる |
| 結果 | コーチと狙い・結果を振り返り、指標と根拠を確認する | 数値の分母と条件を辿れ、未確認のことと次回の確認を区別できる |
| 履歴・データ | 提案・実施・結果、本人の目標を確認し、書き出す・復元する・削除する | 再訪で引き継がれ、目標や希望も本人が編集・削除できる |

見た目は落ち着いた作業用ツールを想定する。スピード練習では短い試行の時間や自己記録を見せ、速さに挑戦できるようにする。ほかの練習にも同じ速さを要求する演出は使わず、ランキングは初期優先度を下げる。ガイドを隠しても練習でき、結果の違いを色だけで伝えない。

計画・実施・結果を残すトレーニングノートを内部のメンタルモデルとする。画面は機能名・データ・操作を中心に構成し、タグラインや文章調の見出しを表示しない。PCの白黒を基調とする画面で、セット・指標・根拠を見比べる。強い枠と硬い影は主操作へ絞り、練習中は入力へ集中できる構成にする。[UI設計方針](design-direction.md)

## コーチ体験の最小構成

1. 履歴と本人の目標・時間を読み、比較可能な集計を取得する。
2. 根拠ID、狙い、4種の練習ブロック、時間、教材、確認課題を含むセットを提案する。
3. 「今日は3分」「正確性を重視したい」等を受け、新しい版のセットへ変更する。
4. 教材ID、根拠、合計時間、本人の制約を検査し、本人が選んだセットを開始する。
5. 狙いに対する結果を振り返り、次回の確認項目とともに保存する。

会話を一往復できるだけでなく、計画と実際の練習を結ぶところまでをMVPとする。数値の計算は分析処理が行い、LLMは比較操作を選んで解釈・提案する。自由なSQL・コード実行、無制限の会話履歴、複数モデルの同時対応は初期範囲に入れない。

無効な出力、存在しない根拠や教材、時間超過は検出して提案へ反映しない。再試行できない場合は標準セットへ戻し、コーチが利用できないことを表示する。保存済みの計画や入力記録は失わない。

## 4種類の最小構成

以下の実施方法・評価方法は、コンセプトをMVPとして具体化するための仕様案。

| 種類 | MVPでできること | 結果に示すもの |
| --- | --- | --- |
| スピード練習 | 慣れた短い並びを限界速度で反復する。ミスで入力を止めない | 同条件での入力速度、対象に対して正しく打てた量、誤り候補数 |
| 正確性練習 | 正確さを優先して打ち、条件を保てる範囲で最高速度を試す | 修正前を含む正確さ、修正操作、条件を満たした試行の速度 |
| 苦手練習 | 観測された苦手候補を選び、並び・単語・文で反復する | 対象の誤り候補率、修正量、別文や後日の確認結果 |
| 新パターン練習 | 未習熟の並びを確認し、ガイドあり・なしで練習する | ガイドの有無、自力での入力結果、後日の再現 |

正確性練習の条件は、修正後の最終文字列だけで判断しない。修正前の誤りを十分に判定できない場合は、判定範囲を明示し、条件を満たした最高速度の認定を保留できるようにする。正確さの閾値や速度を上げる幅は、現時点で固定しない。

新パターンの候補には、教材の練習履歴と本人の選択を使う。未出題という理由だけで「まだ打てない」と決めない。初期のガイドは入力列の表示・非表示で構成し、習得済みとする条件は検証で決める。

診断と効果確認は、4種類に共通する条件で行う。新パターンを学ぶ教材と、練習した並びを別の文章で確かめる未見教材は、役割を分けて管理する。

## 教材

初期目安は、短い並びのドリル、数十語、40〜60本程度の短文。実装の最小検証ではさらに少なく始め、公開前に対象キー・組み合わせの出題不足を確認する。数そのものを品質基準にしない。

| 種類 | 例 | 注意点 |
| --- | --- | --- |
| 日本語の読み | 「変更の理由を説明してください」 | 表記・読み・正解経路を監修する |
| 英単語 | `typing`, `prompt`, `README`, `configuration` | 大文字やShiftの条件を明示する |
| 記号 | `()`, `[]`, `/`, `:`, `-`, `_`, バッククォート | まず基本記号に絞り、JIS/USでガイドを変える |
| 混在文 | 「APIの仕様をREADMEに追記する」 | どの範囲をローマ字・英字で打つか表示で区別する |

教材には`exerciseId`、版、表示文、読み、英字として打つ範囲、難度、対象となる並び、適した練習の種類、練習用/評価用の区分を持たせる。すべて自作または利用条件を確認したものを使う。既存サービスの教材を転用しない。

練習教材と効果測定教材を分ける。評価時は未見文を使い、長さ・記号・対象の並びの密度を揃える。同じ短文の暗記による速さを、そのまま汎用的な改善としない。

## 入力エンジンの要件

### ミスを残せる入力

短いフレーズごとに編集可能な入力欄を設ける。誤ったキーを必ず弾いて正解まで進ませない方式は、転置や後からの修正を観測しづらいため、標準方式にしない。入力した誤りも一旦残し、Backspace、Delete、選択置換、カーソル移動を記録する。誤りが残った状態での確定も扱い、最終結果と修正前を区別する。スピード練習では、その場での修正を必須にせず、ミスを含む試行も保存する。

入力欄は標準的なフォーカス・キーボード操作を維持する。計測のためにブラウザや支援技術のショートカットを広く奪わない。

### 正解が複数あること

日本語の読みを、一つの固定ローマ字列だけに対応させない。小書き文字、促音、撥音、語境界を含め、サポート範囲を明示してテストする。入力された有効な経路に対して比較し、`shi`と`si`のような長さの違いを誤りや改善と誤認しない。

実装候補は許容表記を表す状態機械/グラフと、短い入力の編集履歴の対応付け。自由編集と複数経路の組み合わせが信頼できるかを、最初の技術スパイクで確認する。許容経路をすべて文字列として展開することは前提にしない。

難しい表記を未対応にする場合は、その表記を必要とする教材を外し、対象範囲を説明する。妥当な表記を「タイポ」として診断する状態では公開しない。

### 計測できる範囲

キー位置と入力された文字・編集は別の情報として扱う。`keydown.code`だけで日本語の確定文字や使った指を決めない。実際の入力は`input`等の編集情報と照合し、IMEが入った場合や観測が不足した場合には、精密な診断から外す。[調査と仕様出典](research/learning-and-measurement.md)

練習欄にフォーカスがある期間だけ記録する。ページ外・他アプリ・パスワード欄は収集しない。ペースト、ドロップ、自動入力、キーリピート、IME変換は通常の単発打鍵と区別する。フォーカス喪失や長い中断を、誤りや速さの向上として扱わない。

## 結果に出す指標

指標の定義、分母、計測対象モードを表示する。同じ名前で異なる式を混在させない。4種類の記録は、練習の種類・対象・ガイドの有無を揃えて比較する。詳細な計算規約と例は、入力スパイクの結果を踏まえて固定する。

| 指標 | 何を伝えるか | 比較時の条件 |
| --- | --- | --- |
| 修正前を含む正確さ（判定可能範囲） | 直して消えた誤入力も含め、どの程度正しく打てたか | 許容する正解経路と修正履歴を考慮し、判定できた割合も表示する |
| 最終文字列の正確さ | 確定時に誤りが残っているか | 修正前を含む正確さと併記する。修正したミスを消さない |
| 修正操作数/100入力文字 | Backspace、Delete、置換などの負担の代理指標 | 削除キー数と実際に削除された文字数は区別する |
| 正しい入力文字/分 | 修正時間を含め、正しく入力できた量 | ローマ字表記・教材・モードを揃える。日本語WPMへ無理に換算しない |
| 並びごとの誤り候補率 | 文字・2〜3文字の並びのどこが弱そうか | 対象の出題回数を分母とし、件数を表示する |
| 正しく打てた並びの所要時間 | 苦手が速度にも現れていそうか | 修正・中断・リピートを含まない比較可能な観測に限定する |

自由編集と複数ローマ字経路では、入力意図を一意に復元できない場合がある。正しい文字を削除した編集を、必ず誤入力の修正だったとは扱わない。判定不能な内訳を無理に補完せず、計測カバー率を表示する。転置1件という分類と、2文字が入れ替わった文字単位の誤り数も区別する。読み単位/分の併記を検討し、短いローマ字表記へ変えただけの変化を速度向上としない。

修正済みの誤入力を十分な精度で復元できない間は、修正前を含む正確さを単一スコアで出すことを必須にしない。誤り候補の件数、修正操作、最終正確性とカバー率を表示する形に縮小できる。学習の中心となるループを保ち、計測できていない精度を約束しない。

「修正に何秒使ったか」は、迷い・読み直し・削除・再入力が混ざるため、正確な分離が難しい。MVPでは修正操作と総所要時間を主に表示する。削除開始〜再入力完了などの推定を使うなら、定義と「推定」であることを明記する。

総所要時間は測定区間の開始から終了までを一貫して使い、修正時間を都合よく除かない。明示的な一時停止・フォーカス喪失は別扱いにし、評価テストの中断区間は比較対象から除外したことを示す。タイミングの丸めやOS・ブラウザ差があるので、微細な打鍵時間の差を過大に解釈しない。

### タイポの分類

P0は置換、脱落、余分な入力、隣接文字の転置候補を扱う。`ing → ign`は、他の正解経路や編集履歴で説明できないか確認する。複数の解釈がある場合は「転置の可能性」とし、原因を断定しない。

大文字、記号、連続文字、撥音などは分類を誤りやすい。分類不能でも全体の誤りや修正の集計を失わず、精密な内訳だけ「判定できず」とする。

## 個別出題の初期ルール

1. 初回は偏らない診断文を出す。
2. 文字・並びごとに出題回数、誤り候補数、修正、比較可能な所要時間を集計する。
3. 件数と率を併記し、サンプルの少ない項目は弱点の確定対象にしない。
4. 直近の複数セッションで再現した候補を優先し、本人の普段の速度も考慮して今日の一点を選ぶ。
5. 苦手練習の教材構成は「対象を含む教材60%、既習内容20%、広く試す教材20%」を初期案とする。他の種類へは一律に適用せず、4種類間の時間配分も固定しない。
6. 次回の評価で変化を確認し、改善した対象を少し間を空けて再確認する。

メニューは練習の種類と対象を提案し、本人も選び直せるようにする。普段の弱点候補は、診断・共通の確認課題を中心に集計する。限界速度で生じたミスと新パターンを覚え始めたときのミスは、条件別に残して確認課題と照合する。

サンプル不足の仮案は、30回未満の出題、3回未満の誤り候補、2セッション未満の再現のいずれかに該当するもの。これは統計的な確定基準ではない。最初のセッションでは仮候補として出題し、十分な観測が無いのに苦手のランキングを断言しない。

数値の計算と候補の抽出は、理由を説明できる処理で行う。LLMは集計ツールを通して比較・提案し、時間等の制約を満たすセットへまとめる。専用モデルの追加学習や複雑な強化学習は初期要件にしない。

## データと保存

| データ | 主要項目 | MVPの扱い |
| --- | --- | --- |
| 設定 | 配列、入力方式、ガイド、目標 | ローカル保存 |
| セッション | ID、日時、入力モード、配列、実際の表記経路、端末・ブラウザ条件、練習の種類と目標、ガイド有無、教材版、分析版、指標、計測状態 | 比較条件をセッション時点のスナップショットとしてローカル保存 |
| 根拠 | ID、対象、期間、条件、分子・分母、元セッション参照 | 提案から辿れるようにする |
| 目標・希望 | 目標、使える時間、重点、本人の感想 | 観測と区別し、本人が確認・編集・削除できる |
| コーチの計画 | 計画IDと版、狙い、練習ブロック、根拠参照、モデル・schemaの版 | 変更前後、本人が選んだ版、実施結果を関連付ける |
| 振り返り | 結果、未見・後日の確認、次回の確認項目 | 次の提案へ引き継ぐ |
| 生イベント | 経過時間、キー位置、入力/削除の差分、選択範囲、フォーカス/IME状態 | 原則として直近30セッションまたは30日までの短い方を保持する案 |
| 弱点の集計 | 対象、出題数、誤り候補数、適格な時間統計、最終練習日 | ローカル保存。根拠件数を維持 |
| 教材 | 監修済み文、読み、許容経路、区分、版 | 配信物に含める |

保持期間は実測容量を見て調整する。生データを消したあとの再分類には限界があるので、分析版を残して新しい定義の結果と混ぜない。入力中の中断やブラウザ終了も想定して、短いフレーズ単位などで保存する。

提案時の数値・比較条件・根拠参照は計画とともに残す。生イベントの保持期間を過ぎたミスの詳細例は再生できないことを表示し、存在しない詳細へリンクしない。設定変更や別端末からの読み込み後も、現在の設定で過去のセッション条件を上書きしない。

IndexedDBは永続保存の保証ではない。ブラウザの消去、容量制約、プライベートモードなどを説明し、保存失敗時には練習を続けられても未保存を表示する。必要に応じて永続化要求を検討するが、手動バックアップの代わりにはしない。[ストレージの仕様](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

書き出しJSONには`schemaVersion`、出力日時、設定、セッション、集計、目標、根拠、計画と結果を含める。読み込み時は構造・サイズ・版・ID重複・参照の整合を検証し、上書き範囲を見せる。任意のHTMLやコードを教材として実行しない。バックアップファイルは通常のファイルとしてユーザーが保管する。

MVPの標準では打鍵・文章・セッション集計を運営者へ送信しない。配信ホストに残るアクセスログまで「一切のデータが外へ出ない」とは表現しない。効果検証は、希望者が表示内容を確認した集計を書き出す方式から始める。

## 公開前の受け入れ条件

| 項目 | 検証すること |
| --- | --- |
| 日本語入力 | `shi/si`、促音、撥音、語境界など、対象とする許容表記を誤判定しない |
| 混在入力 | 日本語読み・英単語・Shift・記号が指定どおりに入力できる |
| ミスの保持 | 誤入力を修正して最終正解にしても、判定できた修正前の誤りと修正操作が残る |
| 転置候補 | `ing → ign`の未修正・途中修正を扱い、曖昧なものを断定しない |
| 編集操作 | Backspace、Delete、選択置換、カーソル移動で集計が破綻しない |
| 非通常入力 | IME、ペースト、リピート、自動入力を通常の打鍵と混同しない |
| 中断 | タブ移動・フォーカス喪失・一時停止から復帰でき、無効な速度を出さない |
| 個別出題 | データ不足なら候補表示し、対象の選択理由が再現できる |
| コーチ | 選定した方式で、日本語の提案・時間変更・重点変更・振り返りを実際に通せる |
| 根拠と計画 | 数値・根拠ID・教材ID・合計時間を検査でき、説明から根拠へ辿れる |
| 文脈の引継ぎ | 次回に目標と前回結果を引き継ぎ、本人が覚えている内容を確認・変更・削除できる |
| コーチの失敗 | 未対応、取得中、キャンセル、無効出力、推論失敗を区別し、入力・記録を維持する |
| 4種類の選択 | それぞれ単独で開始でき、案内と結果が目的に合っている |
| 種類別の分析 | 限界速度のミスだけで普段の弱点を確定せず、新パターンの初回と定着後も区別できる |
| 正確性条件 | 最終文字列を修正して正解にしただけで、正確に打てた最高速度と認定しない |
| 保存 | 再読み込みで履歴を復元し、書き出し→別環境で読み込み→削除が成立する |
| 保存失敗 | 容量不足やストレージ無効を表示し、保存済みと誤認させない |
| 表示と操作 | JIS/USの案内、キーボード操作、フォーカス、色以外の状態表示を確認する |
| 配信 | HTTPSで公開し、対象外環境への案内と利用・データ保存の説明へアクセスできる |
| 費用 | アカウントの実際の無料枠・失効日・課金条件を確認し、監視と超過時の対応を決める |

自動テストは入力・集計・保存の意味のある境界へ集中する。IMEとOS/配列の差は実機でも確かめる。PlaywrightだけでOSのIMEを完全検証したことにはしない。

## 技術スパイクと公開までの段階

| 段階 | 作るもの・確かめること | 次へ進む条件 |
| --- | --- | --- |
| A: 配信とコーチの検証 | Web Functions + Hono + Vite RSCのproduction build、一方式の日本語LLMコーチ | streaming・hydration・起動・構造化提案・変更指示を確認できる |
| B: 入力と分析の検証 | 複数正解、自由編集、転置候補、根拠IDを持つ集計 | 代表的なケースを記録・再現し、誤判定の範囲を説明できる |
| C: コーチとの学習ループ | 小さな教材、4種類、セット提案・変更・実施・振り返り | 自分で数日使え、提案の理由と結果を確認できる |
| D: 公開β | 履歴、バックアップ、削除、ヘルプ、ホスト設定 | 公開前の受け入れ条件を満たす |
| E: 効果の探索 | 希望者の反復利用と未見テスト | 有用性と限界を確認し、次に投資する機能を決める |

工数と日程は段階A・Bで配信、コーチ、入力計測の難度を確認してから見積もる。MVPの公開と、学習効果の検証完了は別の節目として扱う。

## 判断を変える条件

- ミス分類の精度が足りない場合は、曖昧な分類の表示を控え、信頼できる正確さと修正操作から出題する。
- 利用者が求めるのがIME変換・確定の改善なら、そのモードを先に検証し直す。
- ルール出題より通常練習が良い場合は、適応ルールを見直す。個別最適化を機能名だけで維持しない。
- データ量や画面応答が実測で問題になるまで、DuckDB-Wasmやクラウド分析DBは導入しない。
- 選んだLLMが日本語の提案・変更を満たせなければ、提供方式か対応環境を見直す。AIコーチを検証せずに中心価値が完成したとは扱わない。
- 数値計算と学習効果の評価は、検証可能な分析処理に残す。
