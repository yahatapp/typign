# Typign MVP後の機能拡張計画

作成日: 2026-10-24。実装の基準: `c6ac8e5`（ローカルMVP）。本書は追加開発の提案。

**次の開発では、未見文と後日の確認によって「練習した結果」を分かりやすくし、その土台の上で自作教材、コーチ、利用環境を広げることを提案する。** データ保護と入力性能の改善は、この機能開発と並行して進める。

対象は、引き続き日本語・英語・記号を使うPC利用者とする。ログインせず練習できること、個人データを端末内に置くこと、運営がLLMの推論を提供・負担しないこと、白黒を基調とする画面、Hono・Vite/RSC・AWSという構成を維持する。同期など、この前提を広げる機能には個別の設計判断を置く。

## MVPの未検証事項を先に閉じる

入力、4種類の練習、計画の版管理、保存・復元の実装はある。一方、次の項目は既存の[MVP仕様](mvp-scope.md)に含まれる未検証事項である。新機能の実装と並行して確認できるが、AIコーチの完成や公開の判断には確認結果が必要になる。

| ID | 残っている確認 | 完了の条件 |
| --- | --- | --- |
| V1 | 実際のChrome内蔵LLMによる日本語コーチ | 対応端末で既存の合成集計20例を実行し、提案・時間変更・重点変更・振り返りの構造と内容を確認する。取得、失敗、キャンセル、練習開始時の中断も記録する |
| V2 | OS・キーボード・IMEの実機確認 | Windows/macOS、JIS/USの確認表を作り、許容表記、Shift記号、削除・置換、IME誤投入を確認する。未確認の組み合わせは明示する |
| V3 | AWS上の配信と公開運用 | 起動、streaming、Flight、直接アクセス、404、HTTPS、個人データを送らない通信、実費を確認し、切り戻しと費用超過時の手順を残す |

現在の端末ではChrome Betaが `unavailable` を返しており、V1は未完了である。対応条件は[Prompt API公式資料](https://developer.chrome.com/docs/ai/prompt-api)で確認し、ブラウザ版、端末、モデル、実行日を記録する。内蔵LLMで要件を満たせない場合は、対象環境または推論方式を見直す判断を行う。標準セットだけでAIコーチを完成扱いにしない。

以降の優先度は本書の提案として、P1を次の改善、P2をその後の拡張、P3を需要・技術検証後の候補とする。MVPの完了条件は既存の仕様を継承する。

## MVPで見送った機能の追加プラン

| ID・優先度 | 機能と最初の範囲 | 着手条件・確認する結果 |
| --- | --- | --- |
| A1・P1 | 入力履歴のリプレイ。文字列、選択範囲、挿入・削除を時系列で再生し、`ing → ign`と途中修正を見返す | 保存済みイベントから再計算した結果と一致する。曖昧な操作は分類保留と表示し、保持期限切れの詳細は再生しない |
| A2・P2 | 自分の文章を教材化。テキストの貼り付け・ファイル読み込み、読みの編集、日本語と英字の区間指定、練習前の入力確認を端末内で行う | 文字数・対応文字・読み・教材IDと版を検証する。HTMLは実行しない。保存するか本人が選べ、削除・書き出しにも対応する。評価教材には使わない |
| A3・P2 | AIによる練習文の候補作成。対象の並び、長さ、仕事の場面を指定し、候補を本人が確認して登録する | A2の教材検証を通す。読み、対象の出現数、長さをプログラムで検査し、意味や読みの自然さは本人が確認する。失敗時は監修済み教材へ戻る。評価文・公開教材への自動採用は行わない |
| A4・P2 | 別の端末内LLMへの対応。まずWebLLMを比較検証し、採用する場合は内蔵LLMと同じ入出力契約を使う | V1と同じ20例で日本語品質、取得容量、待ち時間、メモリ、キャンセル、入力への影響を比較する。モデルの利用条件と配布費用を確認し、常時複数モデルを読み込まない |
| A5・P3 | IME ONの仕事文練習。変換・確定を含む文章入力を別モードで試す | OSごとのイベントを収集して規約を先に定める。最終文、総時間、観測可能な編集を中心とし、IME OFFの速度・誤り率と混ぜない。変換候補の内部状態や誤変換原因は断定しない |
| A6・P3 | 任意のアカウントと端末間同期。まず設定、目標、計画、集計の同期を設計する | 複数端末の需要を確認する。認証・利用者ごとのアクセス制御、競合、削除の伝播、端末紛失、復旧、費用を設計・試験してから提供する。生イベントと自作文章は標準の同期対象に含めない |
| A7・P3 | 高度な技能推定・分析DB。変化の検出、習熟度の確率推定、DuckDB-Wasm/OPFSを個別に検証する | 人手で正解を付けたデータと単純な集計を比較する。予測や説明が改善しない推定は採用しない。分析DBは大量履歴の計測でDexieの索引・集計改善だけでは不足した場合に選ぶ |
| A8・P3 | 会話型の仕事シミュレーション。仕様の追記、レビューへの応答など、段階的に文を入力する | A2とA5の扱いを整理した後、まず固定シナリオで試す。文章を考える時間と打鍵の時間を分け、文章力をタイピング技能の点数に含めない |

WebLLMはWebGPUを使うブラウザ内推論とWorkerへの分離を提供するが、Typignでの日本語品質や対象端末への適合は未検証である。[WebLLM公式資料](https://webllm.mlc.ai/docs/)

外部AIへ相談するための集計コピーは、小さく試せる候補として残す。送信前に含まれる目標・感想・集計を本人が確認・削除できる形とし、自動送信や回答の自動適用は行わない。BYOKや承認を要するChatGPT連携は、利用資格、認証情報の保存、費用負担を別途確認してから判断する。

## コア体験は「何を練習し、どう変わったか」を強くする

### 未見文でも比較できる教材と規約を作る

現実装の自動比較は、教材ID・版、実際の表記経路、モード、ガイド、配列、計測環境まで一致させている。そのため、異なる未見文の結果をそのまま前回比にできない。ここを緩める前に、比較用教材の条件と表示を設計する。

| ID・優先度 | 改善案 | 最初の範囲と完了条件 |
| --- | --- | --- |
| B1・P1 | 教材パックと未見文の補充 | 日本語、英語、記号、混在文を版付きで整理する。練習と評価を分け、長さ、対象の密度、記号・大文字の割合を揃えた評価セットを用意する。練習やプレビューで表示済みの文、在庫不足、教材廃止時の履歴参照を試験する |
| B2・P1 | 同一文の記録と、別文への広がりを表示 | 同一条件の記録は現規約を維持する。別文の確認はB1の比較セットIDと条件を保存し、分子・分母、件数、カバー率、表記の構成を並べる。異なる文の単純な速度差を改善率として出さない |
| B3・P1 | 後日の確認リスト | 既存の24時間後の候補抽出を画面へつなぎ、対象、前回の計画、確認予定、未見文の残数を表示する。延期・見送りを選べ、未実施と失敗を区別する。まず翌日以降の確認を使い、間隔の最適化は検証後に行う |
| B4・P1 | 計測対象の並びを増やす | 現在の教材タグ中心の対象から、実際の許容経路に対応する2〜3文字、記号や言語の境界へ段階的に広げる。観測機会と帰属の曖昧さを検証し、サンプル不足は仮候補にする |

未見の条件は「そのブラウザに履歴がないこと」だけでは十分でない。バックアップ復元、自作教材との重複、教材の改版、将来の同期でも出題履歴を引き継ぐ。確認に使える文がない場合は不足を表示し、既出文を未見と呼ばない。

### 本人が提案を調整し、根拠を読み取れるようにする

| ID・優先度 | 改善案 | 最初の範囲と完了条件 |
| --- | --- | --- |
| B5・P1 | 比較条件と根拠を読みやすくする | 期間・対象で絞り込み、配列・表記・ガイド・教材版を短いラベルで示す。現在の条件キーの文字列は詳細へ移す。グラフには件数、除外理由、比較できる範囲を付ける |
| B6・P1 | 計画の変更を見える形にする | ブロックごとの時間・順番・対象と、避けたい内容を編集し、変更前後のブロックと根拠を確認して開始できる。AIが使えない場合にも調整でき、実施した版が履歴に残る |
| B7・P2 | 四つの練習の進め方を増やす | スピードは短い試行と休憩、正確性は条件を満たす速度への段階的な挑戦、苦手は並び→単語→文、新パターンはガイドを段階的に減らす方式を試す。方式を比較条件に残し、設定変更で過去の記録を混ぜない |
| B8・P2 | コーチへ渡す希望を選ぶ | 目標・感想を項目ごとに選び、優先度、有効期限、一時除外を設定できるようにする。本人の希望と観測結果を分けて表示し、編集・削除を次回に反映する。疲労は自己申告として扱う |

苦手練習の60/20/20構成と、30機会・3誤り候補・2セッションという初期条件は、まず比較の基準として残す。変更時にはルールの版を保存する。修正前正確性の単一スコア、修正損失秒数、自動の習得認定は、対応する観測と妥当性の確認が揃うまで保留する。

## コア機能外では、再訪とデータの持ち出しを助ける

| ID・優先度 | 追加案 | 最初の範囲・評価すること |
| --- | --- | --- |
| C1・P1 | 初回案内と計測ヘルプ | 配列、IME OFF、未保存、比較除外、未見文の意味を操作に沿って説明する。案内を閉じた後に本人が単独で診断・保存へ進めるか確認する |
| C2・P2 | 週次の振り返り | 端末内で練習内容、確認できた変化、未確認の対象をまとめる。文章の定型版から始め、AI要約は任意とする。休んだ日を失敗と表示しない |
| C3・P2 | PWAとオフライン起動 | 必要な共通画面・公開教材を保存し、読み込み済み画面での通信断対応から、再起動できる範囲へ広げる。モデル未取得時、キャッシュ更新、旧教材版、保存中の更新を試験する |
| C4・P2 | 控えめな再訪支援 | アプリ内の確認予定、本人が選ぶ曜日、休止を用意する。OS通知は需要とブラウザ制約を確認後の任意設定とし、連続日数の維持を優先させない |
| C5・P2 | 表示と操作の調整 | 文字サイズ、行間、動きを減らす設定、入力外のショートカットを用意する。入力中のキーを操作に奪わず、白黒の画面でも状態が区別できるか確認する |
| C6・P2 | 記録の整理・書き出し | 感想へのタグ、期間検索、集計CSV、共有用の匿名要約を追加する。個別記録の削除は関連する根拠・計画への影響を示してから行う。JSONバックアップとは用途を分ける |
| C7・P1 | 不具合報告用の情報出力 | アプリ版、ブラウザ、配列、エラー種別を本人が確認してコピーできる。教材本文、目標、感想、生イベントは標準で含めない |

PWAのオフライン機能はService Workerなどで構成できる。RSCの通信をそのまま無期限保存する設計は避け、版が揃う教材と起動用画面の範囲を定める。モデルの取得状態も別に表示する。[MDN: オフライン動作](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation)

チーム管理、公開ランキング、対戦、課金、教材市場は、継続利用や支払意思を確認してから再検討する。モバイルは当面、記録閲覧や設定の候補とし、PCの精密計測の対応範囲には含めない。他アプリの打鍵収集、カメラによる指・目線の評価、汎用チャットは今回の追加計画に含めない。

## 非機能は公開前から継続して拡充する

| ID・着手時期 | 拡充する部分 | 実施内容・受け入れ条件案 |
| --- | --- | --- |
| N1・最初 | 入力性能 | 基準端末で、キー入力から文字表示までの時間、入力欠落、分析中の長い処理、モデル推論との干渉を測る。仮の目標は95%の入力が収まる時間（p95）で50ms以下・入力欠落0件。端末と測定方法を先に固定し、重い分析は入力確定後やWorkerへ移す |
| N2・最初 | 保存・復旧 | 容量の表示、永続化要求の可否、バックアップの案内、DBの版移行を追加する。容量不足、途中終了、旧版からの移行失敗でも既存データを破壊しない。複数タブによる更新競合を検出する |
| N3・最初 | 計測の再現性 | 実機の編集例に人手で期待結果を付け、自動再生と照合する。許容経路、修正、転置候補、曖昧な編集、時刻、保持期限、復元境界を継続検査する。分析版の更新で過去の数値を黙って上書きしない |
| N4・最初 | プライバシーと安全性 | 個人データの送信経路、アクセスログの項目・保持期間、依存関係、セキュリティヘッダーを確認する。自作文章や感想をLLMへの命令と区別し、未許可の操作・根拠ID・教材IDを拒否する。報告用ログへ本文や個人集計を出さない |
| N5・最初から | アクセシビリティ | WCAG 2.2 AAを目標とし、キーボード操作、フォーカス、コントラスト、200%拡大、読み上げ、タイマー・状態通知を自動検査と手動操作で確認する。入力欄の変更を毎打鍵で読み上げない。適合の表明は監査後に行う |
| N6・公開前 | 配信と運用 | AWS構成をIaCで再現できるようにし、検証環境と本番、最小権限、配信版、切り戻し、死活・エラー・費用監視を整える。料金アラートだけで課金を止められるとは扱わず、流入制限や停止の手順も用意する |
| N7・最初から | 開発とリリース | CIで型検査、単体テスト、本番ビルド、E2E、配信用パッケージの起動確認を実行する。教材・schema・分析・プロンプトの変更を区別し、失敗ケースとデータ互換性をリリース条件に含める |
| N8・履歴拡大前 | 大量データと保守性 | 100・1,000・10,000セッションの合成データで起動、検索、集計、書き出し・復元を測る。全件読み込みを必要な範囲の読み込みへ変え、索引と集計の保存を検討する。画面・保存・コーチの処理を分割し、入力エンジンの独立性を保つ |

N1の数値は、最初の計測で妥当性を確認する受け入れ条件案である。N8の履歴件数は負荷試験用の規模とし、生イベントは直近30セッションまたは30日の短い方までという現行の保持条件を守る。

ブラウザのストレージは容量制限や消去の対象になるため、永続化要求を追加してもバックアップは必要になる。[MDN: 保存容量と消去](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) アクセシビリティの確認対象は[WCAG 2.2](https://www.w3.org/TR/WCAG22/)を基準に具体化する。

## 実装は四つの段階に分ける

| 段階 | 主な項目と依存関係 | 次へ進む条件 |
| --- | --- | --- |
| 0: 検証と保護 | V1〜V3、N1〜N7の初期対応、C1・C7。機能追加とは別にMVPの確認結果を更新する | 公開に必要な実機・配信・保存・コーチの確認結果が揃い、対象環境と未対応範囲を説明できる |
| 1: 練習結果が分かる | B1→B2→B3、B4〜B6、A1。教材と計測を先に整え、後日の確認と説明をつなぐ | 提案→実施→未見文→後日の確認を辿れ、本人が比較条件と次の練習の理由を説明できる |
| 2: 自分の用途で続ける | A2→A3、B7・B8、C2〜C6、N8。A4は独立した技術検証として進める | 教材登録、再訪、オフライン、履歴増加でも計測・保存が崩れない。追加機能が利用されたかを確認する |
| 3: 利用範囲を広げる | A5〜A8。同期、IME、推定モデルをそれぞれ別の検証として扱う | 需要、実装費、保守費、データ契約を確認し、採用する項目ごとに仕様と受け入れ条件を決める |

保存schemaの変更は、A2の自作教材やB3の確認予定を増やす前に移行方式を決める。PWAでは起動用画面・教材・schemaの版を揃える。同期はこの移行と競合処理が安定した後に進める。非機能の確認は、各段階の変更内容に応じて繰り返す。

V1を確認できる環境が得られない場合には、A4の比較検証を段階0へ前倒しする。MVPの推論方式を変更する場合は、その判断と実機検証を経て仕様も更新する。

工期は、実機とAWSを確認できる環境、開発人数、既存データの移行範囲が未確定のため固定しない。段階1は、教材の整備、比較規約、再確認の画面を別々に見積もり、最初の実装結果から更新する。

### 最初に作る作業単位

| 順序 | 作業 | 完了時に残すもの |
| --- | --- | --- |
| 1 | V1〜V3とN1〜N7の確認項目を分ける | 実機確認表、実LLMの20例の結果、AWS検証手順、CI設定、性能の基準値、保存移行と切り戻しの方針 |
| 2 | B1の教材・評価セットを設計する | 教材の追加・監修手順、比較セットの条件、出題履歴・在庫不足のテスト |
| 3 | B2・B4の比較と観測を実装する | 同一文・別文の表示規約、並びの抽出と誤り候補の検証例、版付きの集計 |
| 4 | B3の後日確認をセット画面へつなぐ | 確認予定、延期、実施済み、未見文不足の状態と、計画・結果への参照 |
| 5 | B5・B6・A1で説明を整える | 根拠の絞り込み、変更前後の表示、入力リプレイ、保持期限後の表示 |
| 6 | 協力者と段階1の使い勝手を確認する | 練習を選べたか、根拠を理解できたか、保存を理解できたかの観察記録。結果を基に段階2の対象を絞る |

## 投資判断は継続利用と学習結果を分けて行う

まず5〜8名への課題・操作の確認、次に10〜20名・約2週間の探索的な利用を、既存の[調査計画](research/learning-and-measurement.md)に沿って検討する。人数と期間は探索的な利用の案である。効果の強い主張には、より大きい参加者数と並行群など別の試験設計が必要になる。

使い勝手では、診断から練習を始められるか、提案の理由が分かるか、再確認へ戻れるか、保存を理解できるかを見る。学習結果では、複数日の基準値、練習時間を揃えた標準セットとの比較、未見文での修正量と速度、後日の再確認を見る。評価セット・順番・日・表記条件を残し、少人数の前後差から因果効果を断定しない。

改善幅や速度の許容差は、基準値を測った後、比較結果を見る前に決める。希望者が内容を確認した集計を書き出す方式から始め、利用状況の収集を追加する場合は、保存先・送信項目・目的・同意・削除方法を先に定める。

次の開発対象としては、V1〜V3と初期の非機能対応を進めながら、B1の教材・比較セット設計に着手することを推奨する。同期や生成教材への投資は、この確認と段階1の利用結果を受けて決める。
